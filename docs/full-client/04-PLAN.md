## Этап 8. Моды (модули)
Цель: пользователь ставит маленькие расширения (например, «авто-перевод», «скрыть чаты», «быстрые ответы», «тема»), не получая риска утечки сессии.

**Архитектура (обязательно соблюсти):**
* Мод = папка/zip: `manifest.json` `{id, name, version, description, author, permissions:[…], entry:"mod.js", locales?}` + `mod.js`.
* **Песочница**: мод исполняется в изолированном `<iframe sandbox="allow-scripts">` (без `allow-same-origin`) **или** выделенном Worker, **никогда** на странице приложения. У него нет доступа к `window`, `localStorage`, клиенту Telegram, сессии, DOM приложения.
* Общение — только `postMessage` с узким API хоста (`tx.*`), каждый вызов проверяется по `permissions` из манифеста:
  * `messages.read` — получать события новых сообщений (обрезанные поля);
  * `messages.send` — отправка (всегда с подтверждением пользователя в UI);
  * `ui.menu` — добавить пункт в меню сообщения/чата; `ui.panel` — своя панель в слоте (рендерится хостом из декларативного описания, не сырой HTML);
  * `storage` — свой ключ-значение (изолировано по `id`, квота 1 МБ);
  * `net:<домен>` — запросы только к перечисленным доменам, проксирует хост;
  * `theme` — свои CSS-переменные (белый список токенов).
* Установка: из файла/URL; перед установкой показ «модулю нужны права: …» с кнопкой «Разрешить»; список и выключатель в Настройках → «Моды»; аварийный выключатель «отключить все моды».
* Модули не могут менять `telegram.js`, не видят `api_hash`, не получают сессию ни при каких условиях.
**8.1** Хост-API и песочница. **8.2** Манифест, валидация, хранилище модов (IndexedDB). **8.3** Экран «Моды» в настройках. **8.4** Три примера модов в `mods-examples/` (с тестами). **8.5** Документ для авторов модов.
✅ тест: мод пытается прочитать `localStorage`, `fetch` на чужой домен, `window.parent` — всё блокируется; мод с `messages.read` получает событие; без права — нет.
